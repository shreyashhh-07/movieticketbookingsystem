# Database Design

Database: MySQL (`movieticketdb`). Tables are generated by Hibernate from the entity classes (`ddl-auto=update`).

## Tables

### `users` (entity `User`)
| Column | Type | Notes |
|---|---|---|
| **id** | BIGINT, PK, auto-increment | |
| name | VARCHAR(100), NOT NULL | |
| email | VARCHAR(150), NOT NULL, **UNIQUE** | used as login name |
| password | VARCHAR(255), NOT NULL | BCrypt hash, never plain text |
| phone | VARCHAR(15) | optional, 10 digits |
| created_at | DATETIME, NOT NULL | |

### `roles` (entity `Role`)
| Column | Type | Notes |
|---|---|---|
| **id** | BIGINT, PK | |
| name | VARCHAR(30), UNIQUE | `ROLE_USER` or `ROLE_ADMIN` |

### `user_roles` (join table for User ↔ Role)
| Column | Notes |
|---|---|
| **user_id** | FK → `users.id` |
| **role_id** | FK → `roles.id` |

Primary key is the pair (`user_id`, `role_id`).

### `movies` (entity `Movie`)
| Column | Type | Notes |
|---|---|---|
| **id** | BIGINT, PK | |
| title | VARCHAR(150), NOT NULL | |
| genre | VARCHAR(50), NOT NULL | filter field |
| language | VARCHAR(50), NOT NULL | filter field |
| duration | INT, NOT NULL | minutes |
| rating | DOUBLE, NOT NULL | 0 – 10 |
| ticket_price | DECIMAL(10,2), NOT NULL | price of one ticket |
| description | VARCHAR(1000) | |
| release_date | DATE | |
| available_seats | INT, NOT NULL | decreases on booking, increases on cancel |

### `bookings` (entity `Booking`)
| Column | Type | Notes |
|---|---|---|
| **id** | BIGINT, PK | |
| number_of_seats | INT, NOT NULL | |
| ticket_price | DECIMAL(10,2), NOT NULL | copy of the movie price at booking time |
| total_amount | DECIMAL(12,2), NOT NULL | number_of_seats × ticket_price (server-calculated) |
| status | VARCHAR(20), NOT NULL | `CONFIRMED` / `CANCELLED` |
| booking_time | DATETIME, NOT NULL | |
| **user_id** | BIGINT, NOT NULL, **FK → users.id** | who booked |
| **movie_id** | BIGINT, NOT NULL, **FK → movies.id** | what was booked |

## Textual ER Diagram

```
 ROLE                      USER                          MOVIE
 id (PK)                   id (PK)                       id (PK)
 name                      name, email, password ...     title, genre, language ...
  │ *                       │ 1                            │ 1
  │                         │                              │
  │      USER_ROLES         │                              │
  └──── user_id (FK) ───────┘                              │
        role_id (FK)                                       │
                            │ 1                            │
                            │                              │
                            │ *                            │ *
                          BOOKING ─────────────────────────┘
                          id (PK)
                          user_id  (FK → users.id)
                          movie_id (FK → movies.id)
                          number_of_seats, ticket_price, total_amount, status, booking_time
```

In words:
- One **User** can have many **Bookings**; each Booking belongs to exactly one User (1 : N).
- One **Movie** can have many **Bookings**; each Booking is for exactly one Movie (1 : N).
- **User** and **Role** are many-to-many: a user can have several roles, a role belongs to many users.
- Booking is the "many" side of both relationships, so it holds the two foreign keys.

## JPA Mapping

```java
// Booking.java  (owning side - contains the foreign keys)
@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "user_id", nullable = false)
private User user;

@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "movie_id", nullable = false)
private Movie movie;

// User.java  (inverse side - no column of its own)
@OneToMany(mappedBy = "user")
private List<Booking> bookings;

// Movie.java (inverse side)
@OneToMany(mappedBy = "movie")
private List<Booking> bookings;

// User.java - many-to-many with a join table
@ManyToMany(fetch = FetchType.EAGER)
@JoinTable(name = "user_roles",
           joinColumns = @JoinColumn(name = "user_id"),
           inverseJoinColumns = @JoinColumn(name = "role_id"))
private Set<Role> roles;
```

- `@ManyToOne` + `@JoinColumn` → creates the foreign-key column on the "many" table.
- `mappedBy = "user"` → tells JPA the relationship is already mapped by the `user` field in `Booking`, so no extra table/column is created.
- `LAZY` → related rows are loaded only when needed. `roles` is `EAGER` because Spring Security needs them at login.
- `@JsonIgnore` on the `bookings` lists and DTO responses prevent infinite JSON loops (User → Booking → User ...).

## Integrity rules implemented in code
- Email is unique (DB constraint + check in `AuthService`).
- A movie or user that still has bookings cannot be deleted (HTTP 409).
- Cancelling a booking keeps the row (`status = CANCELLED`) so booking history is not lost.
- Seat counts are updated while the movie row is locked (`PESSIMISTIC_WRITE`) so two users cannot book the same last seats.
